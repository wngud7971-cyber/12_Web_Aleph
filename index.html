2023년부터의 시험 준비 고난과 변화

한두 점 앞에서, 방법을 돌아봤습니다.

2023년부터 정보처리기사 실기를 준비했습니다. 세 차례 한두 점 차이로 떨어졌고, 보안 프로젝트와 공부를 함께 하느라 쓸 수 있는 시간도 넉넉하지 않았습니다. 전 범위를 놓치지 않으려 했지만, 같은 방식으로 비슷한 결과를 받은 뒤에는 준비하는 방법을 돌아봐야 했습니다.

기출문제와 자바 문법에 우선순위를 두기로 했습니다. 적은 시간을 여러 곳에 나누기보다, 먼저 이해해야 할 부분에 모으는 선택이었습니다. 오래 노력한 사실에만 기대지 않고, 지금 가진 조건에서 무엇을 바꿀 수 있는지 생각하기 시작했습니다.

2026.09.09 — 09.10 다시 시도한 날

전날 끝내지 못한 과제로 돌아갔습니다.

9월 9일에는 전날 마무리하지 못한 2번 과제를 다시 붙잡았습니다. 로직 오류와 해상도 문제를 직접 해결했고, 목표로 한 제출을 마쳤습니다. 그날 기록에 “어제 마무리하지 못했지만 오늘은 성공했으니 다음 과제에서 더 노력하자”라고 적었습니다. 실패한 하루 다음에도 할 수 있는 행동이 남아 있었습니다.

다음 날에는 가벼운 오류를 혼자 해결하려고 서두르기보다 LLM과 조원의 도움을 받았습니다. 웹사이트를 만드는 조별 과제에서도 의견을 제시하며 프로토타입을 만들었습니다. 제가 아는 것을 보태고, 모르는 것을 함께 살피는 과정은 문제를 푸는 또 하나의 방법이 되었습니다.

2026.09.22 — 10.01 더 나아진 지금

조급함을 다음 행동으로 바꾸고 있습니다.

9월 22일에는 과제가 예상보다 길어져도 원인을 차근차근 찾으려 했습니다. 수업에서는 강의와 실습에 집중하고, 중간 시간을 활용해 8번 과제를 제출했습니다. 마음이 급해질 때에도 할 일의 순서를 정하고, 그 순서에 맞춰 움직이는 연습을 이어갔습니다.

이런 방식은 이전 SecuriCare 프로젝트의 경험과도 이어집니다. 로그가 전달됐는데 화면에서 일부 필드가 빠졌을 때, 인덱스와 로그 필드를 비교해 형식 충돌을 찾고 Filebeat와 파이프라인을 수정했습니다. 원인을 확인하고 결과까지 검증한 과정 은 제가 함께 일할 때 보여줄 수 있는 구체적인 근거입니다.

8월 11일부터 10월 2일까지 남긴 36일의 리추얼 기록에는 아침의 계획과 마무리의 돌아봄이 함께 있습니다. 기록한 날마다 강점 행동을 실천했다고 적었지만, 그것이 모든 날을 완벽하게 보냈다는 뜻은 아닙니다. 끝내지 못한 일을 인정하고 다음 시도로 이어간 날도 있었습니다.

10월 1일에는 논문을 수정하면서 AI에게 맡길 부분과 스스로 생각할 부분을 구분하려 했습니다. 이해되지 않는 내용을 질문하고, 답을 받은 뒤 다시 피드백했습니다. 차분하게 행동하는 자기조절력, 도움을 주고받는 대인관계력, 막힌 과제로 돌아오는 자기동기력을 실제 작업 속에서 계속 기르고 있습니다.

02 / Featured troubleshooting

SecuriCare
화면에서 사라진 로그 필드를 찾다.

2025.11.24 — 2025.12.24 가상 병원 환경의 교육용 모의해킹 프로젝트.

로그는 전달됐는데, 왜 필요한 필드는 보이지 않을까?

Suricata와 WAF에서 수집한 보안 로그가 Elasticsearch까지 전달됐지만, Kibana에서 일부 필드가 누락됐습니다. 인덱스 구조와 로그의 형식을 비교해 원인을 확인하고, 수집과 처리 설정을 수정해 시각화가 복구되는지 확인했습니다.

대상과 범위
가상 병원 Web · Mobile 환경 교육용 프로젝트에서 수행
담당 역할
Wazuh · ELK 통합 로그 환경 구축 웹 취약점 진단 · 대응, 보고서 구조 설계
이 사례의 핵심
인덱스와 로그 필드 비교 수집 파이프라인 수정 및 결과 확인
Suricata · WAF → Filebeat · Pipeline → Elasticsearch → Kibana
  1. 01

    문제 확인

    로그는 전달됐지만 대시보드에서 특정 필드가 빠져 있었습니다. 데이터 전달과 표시 결과를 구분해 살폈습니다.

  2. 02

    구조 비교

    Elasticsearch 인덱스 구조와 들어온 로그의 필드를 단계적으로 비교·분석했습니다.

  3. 03

    원인 특정

    로그 데이터 타입과 Elasticsearch 매핑 사이의 충돌을 확인했습니다.

  4. 04

    설정 수정

    Filebeat 설정과 로그 수집 파이프라인을 수정하고, 데이터 구조를 재정의했습니다.

  5. 05

    결과 확인

    새 인덱스에서 로그 수집을 확인하고, Kibana 대시보드의 시각화가 복구됐는지 확인했습니다.

RESULT

새 인덱스에서 로그가 정상적으로 수집되고, Kibana에서 누락됐던 필드를 확인할 수 있게 됐습니다. 현상을 확인하고 원인을 좁힌 뒤, 수정 결과까지 확인하는 과정을 보여주는 사례입니다.
