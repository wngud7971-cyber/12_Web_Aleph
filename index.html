01 / My story

막힌 상황에서,
다음 행동을 고르기까지.

반복된 시험 결과와 의견이 갈린 프로젝트 앞에서 어떤 선택을 했는지 이야기합니다. 그 선택이 지금의 일하는 방식으로 이어지고 있습니다.

먼저 상황을 정리하고, 함께 다음 순서를 정합니다.

시간이 부족하거나 의견이 다를 때, 먼저 상황을 살피고 다음에 할 일을 골랐습니다. 내용을 공유하고, 일이 막히면 다시 시도하고 해결 방법을 찾습니다.

자기조절력 대인관계력 자기동기력

2024 — 2025 시험 준비와 최종 합격

같은 결과 앞에서, 준비하는 방법을 바꿨습니다.

정보처리기사 실기에서 세 차례 1~2점 차이로 떨어졌습니다. 특히 2025년 11월에 실기 시험을 준비할 때는, 보안 프로젝트와 자격증 공부를 병행하느라 시간이 부족했습니다. 이전에는 모든 범위를 놓치지 않으려 했지만, 한정된 시간 내에서 같은 방식을 반복하면 결과를 바꿀 수 없다고 생각해, 공부하는 방식을 조정했습니다.

기출문제와 자바 문법에 우선순위를 두기로 했습니다. 적은 시간을 여러 곳에 나누기보다 먼저 이해해야 할 부분에 모았습니다. 가진 시간 안에서 무엇을 먼저 할지 정하는 선택이었습니다.

이후 2025년 3차 정보처리기사 실기시험에서 최종 합격했습니다. 이러한 경험을 통해 주어진 시간과 상황을 살피며, 무엇에 먼저 집중해야 할지 정하는 방법을 배웠습니다.

대학 시절 · DB 프로젝트 2025.11 — 12 · SecuriCare

서로 다른 순서를, 함께 일할 기준으로 연결했습니다.

협업에서도 작업의 순서를 조율해야 했습니다. 대학 시절 DB 구축 프로젝트에서 한쪽은 DB 구조를 먼저 완성하자고 했고, 다른 쪽은 웹페이지에 표시할 내용에 맞춰 DB를 수정하자고 했습니다. 설계 변경이 반복되면서 PHP 파트와의 협업도 지연됐습니다.

부팀장 파트의 구성원이었던 저는 다른 파트의 친구에게 먼저 이야기를 건넸습니다. 서로의 요구를 차분히 정리하지 않고 의견을 주고받으면 논의가 길어지고, 프로젝트 완수도 어려워질 것이라고 생각했습니다. 친구와 저는 각 파트와 대화하며 입장을 정리하고 함께 중재했습니다.

DB에서는 핵심 뼈대인 기본키와 외래키가 될 대상을 명확히 정리하고, PHP에서도 기본 내용을 갖춘 뒤 추가적인 내용을 붙이기로 했습니다. 각 파트가 다음 작업을 시작할 기준이 생겼고, 프로젝트를 마무리할 수 있었습니다. 이후에는 제 작업의 영향도와 우선순위를 살피고, 확인한 내용과 남은 문제를 구분해 공유하려 노력했습니다.

2025년 11월부터 12월까지 진행한 SecuriCare에서는 Wazuh·ELK 로그 환경 구축과 웹 취약점 진단에 참여했습니다. 팀원마다 다른 취약점 정리 방식도 중요도와 영향도에 맞춰 통일하고, 진단부터 대응과 검증까지 이어지는 공통 구조를 제안했습니다. 기술적으로 확인한 내용을 다른 사람이 이해하고 판단할 수 있게 전달하는 일도 제 역할이었습니다.

2026.08.11 — 10.02 9월 9일의 재시도와 현재

막힌 일로 돌아가, 다음 행동을 이어가고 있습니다.

제 과제가 막혔을 때에도 다음 행동을 찾아야 했습니다. 2026년 9월 9일에는 전날 마무리하지 못한 2번 과제로 돌아가 로직 오류와 해상도 문제를 해결하고 제출을 마쳤습니다. 그날 기록에는 “어제 마무리하지 못했지만 오늘은 성공했으니 다음 과제에서 더 노력하자”라고 적었습니다.

2026년 8월 11일부터 10월 2일까지 남긴 36일의 리추얼에는 아침의 계획과 마무리의 돌아봄이 함께 있습니다. 하려던 일과 실제 결과를 돌아보고 다음 행동을 기록하며, 끝내지 못한 일을 다음 시도로 이어가고 있습니다.

저는 보안과 시스템 운영 분야에서 문제의 원인을 근거를 바탕으로 분석하고, 서로 다른 요구를 정리해 함께 해결하는 일을 하고 싶습니다. 확인한 내용과 남은 문제를 명확히 공유하고, 동료가 다음 작업을 이어갈 수 있도록 돕겠습니다. 맡은 일이 막혔을 때에도 다시 시도하며 함께 정한 목표를 완수하겠습니다.

02 / Featured troubleshooting

SecuriCare
화면에서 사라진 로그 필드를 찾다.

2025.11.24 — 2025.12.24 가상 병원 환경의 교육용 모의해킹 프로젝트.

로그는 전달됐는데, 왜 필요한 필드는 보이지 않을까?

Suricata와 WAF에서 수집한 보안 로그가 Elasticsearch까지 전달됐지만, Kibana에서 일부 필드가 누락됐습니다. 인덱스 구조와 로그의 형식을 비교해 원인을 확인하고, 수집과 처리 설정을 수정해 시각화가 복구되는지 확인했습니다.

대상과 범위
가상 병원 Web · Mobile 환경 교육용 프로젝트에서 수행
담당 역할
Wazuh · ELK 통합 로그 환경 구축 웹 취약점 진단 · 대응, 보고서 구조 설계
이 사례의 핵심
인덱스와 로그 필드 비교 수집 파이프라인 수정 및 결과 확인
Suricata · WAF → Filebeat · Pipeline → Elasticsearch → Kibana
  1. 01

    문제 확인

    로그는 전달됐지만 대시보드에서 특정 필드가 빠져 있었습니다. 데이터 전달과 표시 결과를 구분해 살폈습니다.

  2. 02

    구조 비교

    Elasticsearch 인덱스 구조와 들어온 로그의 필드를 단계적으로 비교·분석했습니다.

  3. 03

    원인 특정

    로그 데이터 타입과 Elasticsearch 매핑 사이의 충돌을 확인했습니다.

  4. 04

    설정 수정

    Filebeat 설정과 로그 수집 파이프라인을 수정하고, 데이터 구조를 재정의했습니다.

  5. 05

    결과 확인

    새 인덱스에서 로그 수집을 확인하고, Kibana 대시보드의 시각화가 복구됐는지 확인했습니다.

RESULT

새 인덱스에서 로그가 정상적으로 수집되고, Kibana에서 누락됐던 필드를 확인할 수 있게 됐습니다. 현상을 확인하고 원인을 좁힌 뒤, 수정 결과까지 확인하는 과정을 보여주는 사례입니다.
