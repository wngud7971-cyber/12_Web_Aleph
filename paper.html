PostgreSQL 18.6의 100만 행 로컬 실험

배주형
Aleph 과정 과제 10
2026년 10월 2일

초록

선택도가 높아지면 인덱스 스캔이 순차 스캔보다 느려지는지 알아보기 위해, PostgreSQL 18.6에서 100만 행을 반복 측정했다. 선택도 0.1~90%의 원 실험과 테이블 정리 후 95~100% 실험에서 각 조건을 10회씩 측정한 450건을 분석했다. 이후 우위가 불분명했던 80%에서 조건당 30회씩 90건을 추가로 측정했다. 일반 인덱스 스캔과 순차 스캔의 평균 실행 시간은 100%까지 역전되지 않았으며, 80%는 추가 측정에서도 우위를 확정하지 못했다. 테이블이 팽창한 실행과 읽기 블록이 많은 별도 실행에서는 순차 스캔이 빨랐다. 원 실험과 추가 측정의 시스템 상태가 같았는지는 확인되지 않아 각각 분석하고 합산값은 참고로 제시했다. 결과는 설정한 가설을 지지하지 않았으며, 이번 로컬 실험 조건을 벗어나 일반화할 수는 없다.

주제어 PostgreSQL, 선택도, 인덱스 스캔, 순차 스캔, 웜 캐시, 테이블 팽창

1 서론

1.1 연구 질문과 배경

인덱스는 조건에 맞는 행을 찾는 데 쓰인다. 그러나 조건을 만족하는 행이 많아지면 인덱스를 탐색하고 테이블의 행에 접근하는 비용도 커지므로, 모든 쿼리에서 인덱스가 가장 빠른 것은 아니다. 옵티마이저는 이러한 비용을 비교해 접근 경로를 선택한다[1, 2]. 본 연구는 “인덱스를 쓰면 항상 빠른가”라는 질문에서 출발해, 선택도에 따라 두 스캔 방식의 실행 시간이 어떻게 달라지는지 비교했다. 여기서 순차 스캔은 PostgreSQL의 Seq Scan으로 테이블 전체를 읽는 풀 테이블 스캔을 뜻한다.

선택도가 높아질 때 일반 인덱스 스캔보다 순차 스캔이 빨라지는 구간이 나타나는지, 나타난다면 어느 구간인지가 연구의 질문이다. 선행 연구에서는 선택도 외에도 하드웨어, 시스템 설계와 동시 실행 부하가 접근 경로의 성능에 영향을 준다고 보고했다[6]. 이번 실험에서는 선택도를 바꾸면서 나머지 조건을 가능한 범위에서 고정했다.

1.2 선택도와 가설

선택도는 전체 행 중 WHERE 조건을 만족하는 행의 비율로 정의했다. 전체가 100만 행이면 선택도 0.1%는 1,000행, 1%는 10,000행, 50%는 500,000행에 해당한다. 100%는 모든 행이 조건을 만족하는 경우다. 실험에서는 플래너가 추정한 비율 대신 COUNT(*)로 실제 행 수를 확인해 선택도를 맞췄다[2].

실험을 시작할 때 세운 가설은 “선택도가 높아질수록, 인덱스 검색과 풀 테이블 스캔 간의 실행 시간 차이가 줄어들다가 역전된다”이다. 결과를 확인한 뒤에도 이 가설 문장은 바꾸지 않았다.

가설을 확인하기 위해 낮은 선택도에서는 인덱스가 빠를 것이라는 예측을 P1, 높은 선택도에서는 순차 스캔이 더 빨라질 것이라는 예측을 P2로 정했다. 측정 절차를 바꿔도 결과 방향이 유지되는지는 파일럿에서 P3로 점검했다. 높은 선택도에서도 인덱스가 계속 빠르고 역전이 나타나지 않는다면, 측정한 범위에서 P2를 지지하지 못한 것으로 판단했다.

2 연구 방법

2.1 실험 환경

Windows에 설치한 PostgreSQL 18.6에서 100만 행의 테이블을 사용했다. 기본 키 id는 SERIAL형, 선택도 컬럼은 0·1 값을 갖는 INTEGER형으로 만들고, 모든 구간에서 SELECT * 쿼리를 실행했다. 병렬 실행과 JIT는 끄고 전원 어댑터 연결, 고성능 전원 모드와 배경 프로그램 종료를 유지했다. 본실험은 캐시에 데이터가 남아 있는 웜 캐시 조건을 지향했으나, 일부 실행에서는 읽기 블록이 발생했다.

2.3 데이터 생성

generate_data.py로 100만 행을 한 번 생성했다. 고정 시드 42를 사용해 선택도별 목표 비율을 행 개수로 환산하고, 그 개수만큼 무작위 위치에 1을 배치했다. 나머지 행은 0으로 채운 뒤 COUNT(*)로 각 컬럼에서 조건을 만족하는 행 수가 목표와 같은지 확인했다.

2.4 실행 시간 측정과 판정 기준

모든 구간에서 SELECT * FROM experiment_table WHERE {선택도 컬럼} = 1을 실행했다. EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)이 보고하는 Execution Time을 서버 실행 시간으로 기록했다. TIMING OFF를 사용하면 노드별 시간은 계측하지 않지만 전체 실행 시간은 측정한다[3]. 따라서 이 값에는 결과를 클라이언트로 전송하고 화면에 표시하는 데 걸리는 전체 응답 시간이 포함되지 않는다.

실행 계획에서 처음 발견한 스캔 노드로 비교 조건이 실제로 적용되었는지 확인했다[4, 5]. 원 실험과 95~100% 실험에서 C1의 150건은 모두 Seq Scan, C2의 150건은 모두 Index Scan이었다. C3는 원 실험의 0.1%와 1%에서 Index Scan, 10~90%에서 Bitmap Heap Scan, 95~100%에서 Index Scan을 사용했다. 80% 추가 측정의 각 30건은 C1 Seq Scan, C2 Index Scan, C3 Bitmap Heap Scan으로 기록되었다. 조건 설정과 모순되는 스캔 노드는 없었다.

실행 순서의 영향을 줄이기 위해 조건과 구간을 무작위로 섞어 교차 실행했다. 순서 셔플 시드는 원 실험에서 42, 95~100% 실험에서 43, 80% 추가 측정에서 44였다. 각 실행 전에는 테이블을 읽지 않는 기준 서버 연산을 측정해 server_ref_ms에 기록했다. 이 값으로 시스템 전반의 느려짐을 살폈으며, 쿼리 실행 시간을 보정하는 데 사용하지는 않았다.

두 방식의 시간 차이는 C1 평균에서 C2 평균을 빼서 계산했다. 양수이면 일반 인덱스 스캔(C2)이, 음수이면 순차 스캔(C1)이 평균적으로 더 빠르다는 뜻이다. 평균 차이가 측정값의 변동에 비해 충분히 큰지도 살폈다. 두 조건의 표본분산을 각각 반복 횟수로 나누어 더한 뒤 제곱근을 취한 값을 차이의 표준오차로 삼고, 평균 차이의 절댓값이 그 2배를 넘을 때 우위로 판정했다. 이는 두 표준오차를 단순히 더하는 방식과 다르다. 계산은 보존 코드의 구현을 따랐으며, 이 기준을 정식 유의성 검정이나 95% 신뢰구간으로 해석하지는 않았다.

원 실험은 11구간×3조건×10회로 330건, 정리 후 95~100% 실험은 4구간×3조건×10회로 120건이다. 이후 80%에서 3조건×30회로 90건을 추가 측정했다. 기존 두 CSV의 repeat_index는 1~10, 추가 CSV는 각 조건에서 11~40이었다. 추가 측정 규칙의 기록·코드 차이는 부록 B.2에 정리했다. 95~100%로 범위를 넓힌 실험과 80%에서 반복 횟수를 늘린 측정은 구분했다.

2.5 본실험 전 점검

본실험에 앞서 plan_check.py로 ANALYZE 없이 EXPLAIN을 실행해 두 접근 경로의 추정 비용이 교차하는 구간을 살폈다. random_page_cost=4.0일 때 일반 인덱스 스캔과 순차 스캔은 10~20%, 비트맵 허용 조건과 순차 스캔은 50~60%에서 비용이 교차했다. 교차 추정이 10% 이상이면 기존 10%p 간격을 유지하기로 했으므로 측정 구간은 바꾸지 않았다. 플래너의 비용은 상대적인 단위로 표현되기 때문에 실행 시간(ms)과 수치 자체를 비교하지 않았다[8].

측정 절차는 pilot_experiment.py의 예비 실험으로 정했다. 인덱스가 없는 50% 선택도에서 연속 30회 실행과 5분 휴식 후 실행을 비교했으며, 워밍업 4건을 제외하면 측정값은 50건이다. 연속 실행의 첫 5회 중앙값은 113.73 ms였지만 마지막 5회에는 333.26 ms로 약 2.93배 늘었다. 휴식 후에도 워밍업 없이 실행한 10회의 평균은 281.50 ms, 워밍업 후 10회는 274.64 ms로 처음 수준에 돌아오지 않았다. 휴식만으로 느려짐이 해소되지 않아 추가 진단을 진행했다.

느려짐이 테이블 접근에서만 발생하는지 알아보기 위해 순수 Python 연산, 테이블을 읽지 않는 서버 연산과 테이블 쿼리를 함께 측정했다. 진단은 연속 실행 120회와 5분 휴식 후 60회로 구성했다. 배터리 상태의 첫 진단에서 앞 20회의 테이블 시간 중앙값은 278.94 ms였고, 전원을 연결한 재진단에서는 66.21 ms였다. 재진단의 앞·뒤 20회 비는 1.03배로 안정되었으며 두 진단 모두 읽기 블록 수는 0이었다. 이에 전원 연결과 배경 부하 통제를 본실험의 고정 조건으로 삼았다. 다만 두 조건을 함께 바꿨으므로 전원만의 효과인지는 구분할 수 없다.

2.6 사전 기록과 추가 실험

예비 실험과 진단에서 드러난 문제를 반영해 설계를 수정했고, 현재 보존된 코드는 그 최종본이다. 사전 기록 원문인 pilot_preregistration.txt는 남아 있지 않아 규칙별 작성 시점은 확인하기 어렵다. 측정값과 판정 계산은 보존된 원자료와 코드로 확인했다.

원 실험의 0.1~90%에서 역전이 나타나지 않자, 더 높은 선택도에서는 결과가 달라지는지 살폈다. 가설 문장은 유지한 채 extend_grid.py로 95, 99, 99.9, 100% 컬럼을 추가하고 run_experiment_extended.py로 측정했다. 이 추가 실험은 원 실험의 결과를 확인한 뒤 계획했다. 인덱스 우위가 더 약해지거나 역전될 것이라는 예측을 P2-ext로 표시하고, 처음 계획한 실험의 가설과 구분해 판단했다.

2.7 추가 컬럼 생성과 테이블 팽창

추가 컬럼은 ALTER TABLE로 추가한 뒤 UPDATE로 값을 채웠다. 이 과정에서 테이블 크기가 73 MB에서 392 MB로 늘었다. PostgreSQL의 UPDATE는 이전 행 버전을 남길 수 있고, VACUUM FULL은 테이블을 다시 써서 불필요한 공간을 회수한다[9]. 팽창한 상태에서 처음 실행했을 때는 읽기 블록이 증가했으며 순차 스캔이 더 빨랐다.

VACUUM FULL로 테이블을 정리하자 크기가 89 MB로 줄었다. 같은 추가 측정 구간을 다시 측정한 결과, 이번에는 일반 인덱스 스캔의 평균 실행 시간이 더 짧았다. 첫 실행은 raw_results_extended_0_confounded.csv로 보존하고, 최종 가설 판정에는 정리 후 결과를 사용했다.

정리 후 테이블이 원래의 73 MB보다 큰 89 MB인 것은 컬럼이 늘었기 때문이다. 두 테이블은 컬럼 구성이 다르므로 원 실험과 95~100% 실험 사이의 작은 시간 차이를 선택도만의 효과로 보기는 어렵다. 두 단계의 수치는 함께 제시하되 이 차이를 고려해 해석했다.

2.8 80% 구간 추가 측정

10월 2일 supplement_80pct.py로 80%만 C1·C2·C3 각 30회 측정했다. 셔플 시드 44로 90회를 무작위 교차 실행하고, 병렬 실행과 JIT는 껐다. 코드는 대상 인덱스가 없으면 생성하고 VACUUM ANALYZE와 CHECKPOINT를 수행한다. 결과와 버전·반복 횟수·시드는 supplement_80pct.csv와 supplement_80pct_meta.txt에 따로 저장했다. 메타데이터에 테이블 크기와 전체 설정은 없어 원 실험과 물리적 조건이 같았는지는 확인할 수 없다.

4 논의

4.1 높은 선택도에서 유지된 인덱스 우위

원 실험의 테이블은 73 MB, 추가 실험에서 정리한 테이블은 89 MB였으며 shared_buffers는 128 MB였다. 테이블이 버퍼 용량보다 작고 본실험이 웜 캐시를 지향했다는 점에서 캐시가 결과에 영향을 주었을 가능성을 생각할 수 있다. 다만 크기를 비교하는 것만으로 테이블과 인덱스의 모든 페이지가 항상 공유 버퍼에 있었다고 알 수는 없다.

random_page_cost는 비순차 페이지 접근의 비용을 추정하는 설정이다. 기본값 4.0에도 상당한 접근이 캐시에서 처리된다는 가정이 포함되므로, 회전식 디스크만을 전제한 값으로 보기는 어렵다[8]. 이번 저장장치와 캐시 상태가 기본 비용의 가정과 달랐을 수 있지만, 그 영향이 얼마나 컸는지는 따로 측정하지 않았다.

100%에서도 인덱스 스캔이 더 빨랐던 이유를 이번 자료만으로 하나로 좁히기는 어렵다. 버퍼 관리, 운영체제 캐시, 데이터의 물리적 배치와 실행 계획의 처리 비용이 함께 영향을 줄 수 있다. 값 1을 무작위로 배치했다는 사실만으로 실제 페이지 접근의 순서나 지역성을 알 수는 없다. 또한 SELECT *에 필요한 힙 접근 비용을 다른 처리 비용과 나누어 측정하지 않았다.

선행 연구[6]은 메모리 중심의 분석 시스템에서도 선택도와 함께 시스템 설계와 동시 실행 조건을 고려해야 한다고 보고했다. 문헌[7]는 메모리와 저장장치의 비용 관계를 다뤘다. 두 문헌은 이번 결과를 해석할 때 고려할 요인을 제시하지만, 이번 PostgreSQL 실험에서 인덱스가 빨랐던 원인을 직접 설명하는 자료는 아니다.

shared_read_blocks는 PostgreSQL 공유 버퍼에서 찾지 못해 읽은 블록 수다. 운영체제 캐시에서 공급된 읽기도 포함할 수 있어 물리 디스크 I/O 횟수와 동일하지 않다[3].

그림 4와 표 7에서는 테이블 정리 전후에 크기와 읽기 블록 수가 달라지고, 더 빠른 스캔 방식도 바뀌었음을 볼 수 있다. 첫 실행은 원 실험과 물리적 조건이 달랐으므로 가설 판정에서 제외하고 기록을 보존했다. 판정에는 테이블을 정리한 뒤 같은 구간을 다시 측정한 결과를 사용했다.

이 변화가 테이블 크기만의 효과인지는 구분하기 어렵다. VACUUM FULL은 공간을 회수하면서 테이블을 다시 쓰기 때문에 물리적 배치도 바뀔 수 있다[9]. 따라서 정리 전후의 결과는 실행 시간뿐 아니라 버퍼 히트, 읽기 블록 수와 테이블 크기를 함께 살펴 해석했다.

별도 파일 raw_results.csv에서도 순차 스캔이 더 빠른 구간이 있었다. 이 파일은 9월 29일 14:04~14:07의 실행으로, 330건 중 324건에서 읽기 블록이 발생했고 30~90%에서는 C1이 더 빨랐다. 여러 기록을 대조했지만 재실행 이유와 당시 테이블·프로세스 상태는 알 수 없었다. 원인이 확인되지 않은 별도 실행으로 보존했으며, 자세한 비교는 부록 B.1에 정리했다.

4.3 연구 범위와 한계

이번 결과는 단일 PC의 PostgreSQL 18.6에서 얻었다. 데이터는 100만 행, 정리된 테이블은 73~89 MB였으며, 테이블이 물리 메모리보다 훨씬 크거나 캐시 적중률이 낮은 환경은 다루지 않았다. Windows에서 운영체제 캐시까지 비운 완전한 콜드 스타트 조건도 측정하지 않았으므로, 그런 환경에서 같은 결과가 나온다고 볼 수는 없다.

쿼리는 SELECT * 한 형태이고, 데이터는 값이 무작위로 배치된 이진 플래그 컬럼이다. Index Only Scan, 실제 업무 데이터의 상관 구조와 여러 쿼리의 동시 실행은 실험 범위에 포함하지 않았다. 추가 측정 구간에서는 컬럼이 추가되어 테이블 구조가 바뀌었고, 파일럿 조치에서는 전원과 배경 부하를 함께 바꿨다. 따라서 이 요인들 각각의 효과를 나누어 설명하기는 어렵다.

80%는 원 실험 10회와 추가 측정 30회 모두 우위가 불분명했다. 추가 측정의 기준 서버 연산 평균은 원 실험보다 높았고, 당시 테이블 크기와 전체 설정은 메타데이터에 남아 있지 않다. 두 실행을 동일 조건의 40회로 취급하지 않고 합산 값은 참고로 제시했다. 보존 코드의 조회 오류와 규칙별 작성 시점의 증거 한계는 추가 측정 후에도 남아 있다.

5 결론

PostgreSQL 18.6의 100만 행 로컬 실험에서는 선택도가 높아질수록 두 스캔 방식의 실행 시간 차이가 대체로 줄었다. 그러나 원 실험의 0.1~90%와 테이블 정리 후 95~100%에서 평균 성능 역전은 나타나지 않았다. 80% 추가 30회에서도 일반 인덱스 스캔의 평균 시간이 짧았지만 우위는 확정하지 못했다. 이번 조건에서는 “선택도가 높아지면 순차 스캔이 더 빨라진다”는 핵심 예측을 지지하지 못했다.

테이블이 팽창한 추가 실험의 첫 실행에서는 순차 스캔이 빨랐지만, 정리 후에는 일반 인덱스 스캔이 빨랐다. 정리 과정에서 크기와 물리적 배치·캐시 상태가 함께 달라질 수 있으므로 이를 한 요인만의 효과로 설명할 수는 없다. 읽기 블록이 많은 별도 실행에서도 순차 스캔 우위가 나타났으나 원인은 확인되지 않았다. 이 기록들을 주 결과와 구분해 보존했다. 이번 결과는 선택도와 함께 테이블 상태를 고려해야 함을 보여주며, 다른 DBMS나 하드웨어, 디스크 접근이 빈번한 환경까지 일반화하기에는 범위가 제한된다.

2. 필요하면 plan_check.py, pilot_experiment.py, pilot_diagnostic.py를 실행해 설계 점검과 진단을
